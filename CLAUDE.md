## Project Overview

This is a React web application for managing FileMaker Server webhooks via the OData API (introduced in FileMaker Server 22.0.4). The app provides a UI to browse FileMaker databases, tables, and fields, then configure webhooks with filters and callbacks to FileMaker scripts.

**Tech Stack:**
- React with Vite
- Tailwind CSS
- shadcn/ui components

**Key Concept:** No local database persistence is needed. All webhook state lives in FileMaker Server itself.

**Architecture Model:**
- FileMaker Server uses an **event-driven, push model** - it sends HTTP POST notifications to external webhook URLs when data/schema changes occur
- This eliminates the need for polling and enables real-time integrations
- This app manages webhook configurations (create, list, edit, delete, test) and can optionally serve as a webhook receiver to trigger FileMaker script callbacks

## FileMaker OData API Architecture

### Authentication
FileMaker OData uses HTTP Basic Authentication. All requests require credentials for a FileMaker account with appropriate privileges.

### Base URL Structure
```
https://{host}/fmi/odata/v4/{database-name}
```

### Core Endpoints Used

**1. Database Discovery**
- `GET /fmi/odata/v4` - List all available databases

**2. Metadata Retrieval**
- `GET /fmi/odata/v4/{database}/$metadata` - Get all tables, fields, and schema info
- Returns FileMaker-specific annotations: FieldID, TableID, AutoGenerated, Global, Calculation, etc.
- ROWID is used as primary key when no unique field exists

**3. Webhook Management (POST-only - Verified)**
- `POST /fmi/odata/v4/{database}/Webhook.Add` - Create webhook
- `POST /fmi/odata/v4/{database}/Webhook.Delete` - Delete webhook
- `POST /fmi/odata/v4/{database}/Webhook.Get` - Get specific webhook
- `POST /fmi/odata/v4/{database}/Webhook.GetAll` - List all webhooks
- `POST /fmi/odata/v4/{database}/Webhook.Invoke` - Manually trigger webhook for testing

**⚠️ IMPORTANT: Only POST method is supported for all webhook operations. GET, PUT, PATCH, and DELETE HTTP methods are NOT supported.**

**4. Script Execution**
- `POST /fmi/odata/v4/{database}/Script.{script-name}` - Execute FileMaker script
- Request body: `{ "scriptParameterValue": "string|number|object" }`
- Response: `{ "scriptResult": { "code": 0, "resultParameter": "..." } }`

### Webhook Configuration

When creating webhooks via `Webhook.Add`, the POST body includes:

```json
{
  "webhook": "https://target-url.com/endpoint",
  "headers": {
    "Content-Type": "application/json"
  },
  "tableName": "TableName",
  "notifySchemaChanges": false,
  "select": "Field1,Field2,PrimaryKey",
  "filter": "Field1 eq 'value'"
}
```

- **webhook**: Target URL where FileMaker Server will send HTTP POST notifications
- **headers**: Optional custom HTTP headers (for authentication tokens, content type, etc.)
- **tableName**: The FileMaker table to monitor
- **filter**: OData v4 filter expression that determines when webhook fires (only matching records trigger)
- **select**: Comma-separated field list to include in webhook payload (reduces data transfer, improves efficiency)
- **notifySchemaChanges**: Boolean for whether table schema changes trigger the webhook

### Webhook Lifecycle & Event Flow

**How Webhooks Work:**

1. **Creation**: Developer creates webhook via `POST /Webhook.Add` request
2. **Monitoring**: FileMaker Server actively monitors the specified table for:
   - Record changes (create, update, delete)
   - Optional schema changes (if notifySchemaChanges is true)
3. **Event Evaluation**: When a change occurs:
   - Filter expression is evaluated against the changed record
   - If filter matches, selected fields are gathered
4. **Notification**: FileMaker Server sends HTTP POST to the webhook URL with:
   - Selected field data in the payload
   - Custom headers (if configured)
5. **External Processing**: Receiving system processes the event in real time

**Testing**: Use `POST /Webhook.Invoke` with specific rowIDs to manually trigger webhooks for testing without modifying actual data.

**Persistence**: Webhooks are persisted by FileMaker Server and survive server restarts. Use `Webhook.GetAll` on app startup to retrieve all existing webhooks.

### Webhook Updates

**Important**: FileMaker OData does not support PUT or PATCH methods for updating webhooks. To update an existing webhook:

1. **Delete** the old webhook using `POST /Webhook.Delete` with the webhookID
2. **Create** a new webhook using `POST /Webhook.Add` with updated parameters
3. **Update external references** - The new webhook will have a different ID, so any systems referencing the old ID must be updated

This pattern is implemented in `fileMakerService.updateWebhook()` which handles the delete+create operation automatically and returns both the new webhook and the old ID for reference tracking.

## Application Architecture

### Core Features to Implement

1. **Database Browser**
   - Connect to FileMaker Server with credentials (HTTP Basic Auth)
   - List available databases from `/fmi/odata/v4`
   - Browse tables within selected database via `$metadata`
   - Display field metadata (name, type, FileMaker-specific annotations: FieldID, TableID, AutoGenerated, Global, Calculation, etc.)

2. **Webhook Manager (Primary Feature)**
   - **List View**: Display all configured webhooks via `Webhook.GetAll`
   - **Create/Edit Dialog**:
     - Webhook target URL input (where FileMaker will send notifications)
     - Custom headers builder (for auth tokens, API keys, etc.)
     - Table selector (dropdown from metadata)
     - Field selector for "select" parameter (multi-select checkboxes from table fields)
     - Filter builder (visual OData v4 filter expression builder or text input)
     - Schema change notification toggle
   - **Test Function**: Manual webhook invocation via `Webhook.Invoke(id)` with specific rowIDs
   - **Delete**: Remove webhooks via `Webhook.Delete`

3. **Webhook Receiver (Optional Backend Component)**

   If implementing script callbacks, the app needs a backend service to:
   - Receive incoming webhook POST requests from FileMaker Server
   - Parse webhook payload (selected field data)
   - Conditionally trigger FileMaker script callbacks via `POST /Script.{name}`
   - Pass appropriate parameters using `scriptParameterValue`
   - Handle script results (code + resultParameter)

   **Options**:
   - Include Node.js/Express backend in this project
   - Document integration with external services (Zapier, Make, n8n)
   - Provide webhook URL that users configure in their own infrastructure

4. **State Management**
   - Connection credentials (server URL, username, password) - store securely in React state/context
   - Current database/table context
   - Active webhooks list (fetched from `Webhook.GetAll`)
   - No local database - all webhook configurations live on FileMaker Server
   - Refresh webhook list after create/delete operations

## Implementation Notes

- All FileMaker API calls require HTTP Basic Auth headers
- Script names cannot contain @, &, / or start with numbers
- Scripts must run without user interaction (server-side only)
- OData filters use standard OData v4 filter syntax (e.g., `Field1 eq 'value'`, `Age gt 18`, etc.)
- Consider using React Context or state management for FileMaker connection details
- Error handling should cover authentication failures, network issues, and FileMaker errors
- The `$metadata` endpoint provides comprehensive schema information - use it to dynamically build UI
- Webhooks are standards-based (OData v4) and work naturally with serverless platforms, iPaaS tools (Zapier, Make), and custom APIs
- Use `Webhook.Invoke` for testing integrations without modifying live data

### ⚠️ CRITICAL: Reserved Field Names in OData Queries

**The `id` field is a reserved word in FileMaker OData and MUST be quoted in `$select` parameters.**

When querying records and selecting the `id` field, always use:
```
$select="id"
```

NOT:
```
$select=id
```

This applies to any OData query that selects the `id` field. Failure to quote it will result in OData parsing errors. This is a FileMaker-specific requirement and differs from standard OData behavior.

## Research Findings and Verified Behaviors

### 1. Webhook Persistence
**Status: VERIFIED ✅**

Webhooks are persisted by FileMaker Server and survive server restarts. This has been confirmed through testing with the `Webhook.GetAll` endpoint which returns all previously created webhooks even after server restarts.

**Implementation**: Use `Webhook.GetAll` on app startup to retrieve all existing webhooks. The app automatically syncs with the server's webhook state.

### 2. HTTP Methods: POST-Only
**Status: VERIFIED ✅**

All webhook operations use POST method exclusively. No other HTTP methods are supported:

- ✅ `POST /Webhook.GetAll` - Works
- ✅ `POST /Webhook.Add` - Works
- ✅ `POST /Webhook.Get` - Works
- ✅ `POST /Webhook.Delete` - Works
- ✅ `POST /Webhook.Invoke` - Works
- ❌ GET, PUT, PATCH, DELETE methods - NOT supported

This has been verified through systematic endpoint testing with all HTTP methods.

**Implication**: Updating webhooks requires delete+create pattern (no native PUT/PATCH support).

### 3. Webhook ID Behavior
**Status: VERIFIED ✅**

- Webhook IDs are sequentially generated integers (1, 2, 3, etc.)
- IDs are unique per webhook
- IDs cannot be set manually
- When updating a webhook (delete + create), the new webhook receives a new ID
- Old IDs are not reused

### 4. Script Discovery
**Status: No dedicated endpoint**

Scripts are part of a "Script" system table in FileMaker OData, but there is no documented GET endpoint to list all available scripts. The `$metadata` endpoint may contain script information, but this is not confirmed in official documentation.

**Workaround Options**:
- Require users to manually enter script names (validate by attempting to call `Script.{name}` with empty body)
- Check if `$metadata` endpoint includes Script table entries
- Parse script names from FileMaker's metadata if exposed through other means

**Constraint**: Script names cannot contain @, &, / or start with numbers.

### 5. Webhook Callback Flow
**Status: Fully Clarified**

FileMaker Server webhooks use a **push/event-driven model**:

1. **Webhook Registration**: Register a webhook with FileMaker Server pointing to an external endpoint URL
2. **Active Monitoring**: FileMaker Server actively monitors the specified table for changes
3. **Event Evaluation**: When data changes occur:
   - Filter expression is evaluated
   - Only matching changes trigger the webhook
4. **HTTP POST Notification**: FileMaker Server sends POST request to your webhook URL containing:
   - Selected field data (as specified in "select" parameter)
   - Custom headers (for authentication, metadata)
5. **External Processing**: Your webhook endpoint receives and processes the payload
6. **Optional Script Callback**: To trigger FileMaker scripts in response:
   - Your endpoint makes a separate POST request to `Script.{script-name}`
   - Pass parameters via `scriptParameterValue` in the request body
   - Handle script results in the response

**Two-Way Flow**: FileMaker → Your Webhook → (optionally) → FileMaker Script

**Architecture Requirements**:

This app serves two distinct roles:

1. **Webhook Configuration Manager** (Client-side React):
   - Browse databases/tables/fields
   - Create/edit/delete webhook configurations
   - Test webhooks with `Webhook.Invoke`
   - View active webhooks

2. **Webhook Receiver** (Backend Service - Optional):
   - Receive incoming HTTP POST from FileMaker Server
   - Process webhook payloads
   - Trigger FileMaker script callbacks when needed
   - Can be: Node.js/Express server, serverless function, or external service (Zapier/Make/n8n)

**Note**: A pure client-side React app cannot receive webhooks. If script callbacks are required, include a backend component or document integration with external webhook receivers.
